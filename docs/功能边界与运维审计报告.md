## 1. 当前系统实际架构（以源码为准）

```
Siri 快捷指令
  └─ POST :8200/api/siri/play (x-siri-token)                     [http-api.js:51]
       ├─ authenticatedClients()>0 → pending.submit → sendPlayRequest
       │     → 选 1 个已认证 WS 客户端（优先非 loopback、否则最近认证）[control-server.js:266-285]
       │     → play.req → iPad 端 siri-control.js
       │        → recoverySearch(同源 /api/search/complex + MoeData 构造 Authorization) [siri-control.cjs:1061-1300]
       │        → extractFirstSong → waitForPlayerControl → player.addSongToQueue(...)
       │        → PlayerControl 暴露的 addSongToQueue [PlayerControl.vue:1830] → OnlineMusicQueue.addSongToQueue(取 URL) [OnlineMusicQueue.js:76]
       │        → playSong → audio.play() [PlayerControl.vue:859,898]
       │        → play.ack → pending 结算 → HTTP 200/504
       └─ authenticatedClients()==0 → offline-command 单槽 → 202 {status:"queued"}
            → 下一条认证连接 onAuthenticated 自动 dispatch [index.js:48-53, offline-command.js:90]
            → 断线重发 queued；状态经 GET /api/siri/commands/:reqId 查询 [http-api.js:89]

同时服务：
  :8080  web-host（静态 dist + /api→6521 反代 + /siri/pair 配对页）[web-host.js]
  :8200  control（/health + ws /ws + HTTP API + /debug/status）[control-server.js, http-api.js]
  :6521  MoeKoeMusic API（api/app.js，--platform=lite）[独立进程]
```

## 3. 当前真正缺少的功能（按 P0/P1/P2）

### P0（影响可靠性/安全，上线前必做）

| 项 | 现状（证据） | 缺口 |
|---|---|---|
| **唯一控制器绑定** | `sendPlayRequest` 只按“非 loopback + 最近认证”选目标，**不检查配对 Cookie**（control-server.js:266-285）；offline `dispatch` 对**任意**认证连接触发（index.js:48-53）；`play.ack` 也从任意客户端接受（control-server.js:160-165 → onAck）。测试 `sendPlayRequest targets the most recently authenticated client only`（control-server.test.js:190-217）恰好证明了“谁后认证谁收到” | **任何打开 WebUI 的设备（手机/另一 iPad/Windows 浏览器）都可能成为播放端、抢走或顶掉目标 iPad**。核心产品边界当前**不满足** |
| **播放成功 ACK 真实性** | `createCommandHandler.execute` 在 `addSongToQueue` 返回 `result.song` 即发 `ok:true`（siri-control.cjs:885-888）；而 `PlayerControl` 暴露的 addSongToQueue 内部 `await playSong(result.song)` 后**无论成败都返回 `result`**（PlayerControl.vue:1830-1844）；`playSong` 中 `audio.play()` 被拒时只弹“播放失败”、`playing=false`、**不抛错**（PlayerControl.vue:906-924） | **服务器记 `succeeded` 但 iPad 无声音的假成功**（与实机“播放失败弹窗但日志 succeeded”现象吻合） |
| **`shouldPlayNext` 错误映射** | 客户端把 `shouldPlayNext` 当 `AUTOPLAY_BLOCKED`（siri-control.cjs:889-892） | 语义错——`shouldPlayNext` 表示“取 URL 失败/无版权自动切下一首”（OnlineMusicQueue.js:183-193），**不是自动播放拦截**，应映射 `PLAY_FAILED` |
| **6521 API 监听全接口 + 防火墙全开** | netstat：`0.0.0.0:6521` + `[::]:6521`（PID 15652，api/app.js 默认 HOST='' 绑定所有接口，server.js:473-477）；两条 “Node.js JavaScript Runtime” 防火墙规则 **Private+Public、TCP/UDP Any** | 局域网任意设备可达酷狗登录/token API；切公用网络/VPN 时 8080/8200/6521 依旧开放。违反既定安全约束 |

### P1（影响长期运维）

- **会话恢复熔断**：session-auth.js 所有失败一律 60s 冷却（:86-91），`AUTH_REJECTED`/`RISK_REQUIRED` 每 60s 无限重试/撞风控（:161-173）。需硬停 + 小时预算。
- **版本管理缺失**：`MoeKoeSiriControl` **不是 git 仓库**（已实测 `git -C . status` → not a git repo），服务端代码零备份、无回滚。
- **`/health` 过薄**：只有 `{ok, protocol}`，无上游/控制器状态（control-server.js:48-50）。
- **`?token=` 查询参数鉴权**：token 进 URL/历史/代理日志（http-api.js:33-34），应删。
- **success-grace 遗留**：`PENDING_SUCCESS_GRACE_MS` + fallbackAck（pending.js:79-86）是多端抢答时代的产物，单控制器后应简化为首个 ack 即结算。

### P2（可选，不阻塞）

- `doctor.ps1` 分层自检（端口 PID 归属、/health、controller 已配对）；看门狗任务（默认不做）；`.env` ACL；`run/dist.prev/` 快照回滚；客户端对 `auth.ok.version` 不匹配打 warn。

## 4. 当前过多或可删除的功能

| 项 | 处理 | 收益/风险 |
|---|---|---|
| `?token=` 查询鉴权 | **删**（P1） | 收益：token 不进 URL/访问日志。风险：低，Header 已够；同步删测试 |
| `PENDING_SUCCESS_GRACE_MS`/fallbackAck | **删**（P2） | 收益：pending 简化。风险：单控制器后同一 reqId 只可能有一个 ack，无竞态；同步更新 pending.test.js 的 grace 用例 |
| `sendPlayRequest` 的 broadcast 回退分支（http-api.js:65） | **删**（P2） | 死路径。`broadcast()` 本身保留（WS 工具+测试用） |
| `shouldPlayNext → AUTOPLAY_BLOCKED` | **改**（P0） | 语义错误，改 `PLAY_FAILED` |
| `isLoopback` 启发式（control-server.js:67-70,274-280） | **删**（随控制器落地） | 被“控制器门禁”取代，不再需要“猜哪台是 iPad” |
| 多端抢答相关的 README/测试描述 | **改** | 随唯一控制器方案重写语义 |
| `probe/probeAll/recoverSession/window.__siri.play` | **保留**（标注维护用） | 不删——是实机验证/维护入口，不进生产路径 |
| `getRouter` provides-fallback、`buildAuthHeaders`、`createPairingLimiter`、`safeTokenEqual` | **保留** | 兼容/安全小件，无过度设计 |

**总评**：没有“必须大删”的整块架构。最大的过度设计是**“多客户端选目标/防抢答”这一整套启发式**（非 loopback+最近认证+success-grace+失败 ack 等待），它是在“无法确认谁是真 iPad”的前提下打的补丁；一旦唯一控制器落地，整套可删掉大半。其余为小件。

## 5. 唯一目标 iPad 绑定方案（最终选定）

**方案：服务端 `run/controller.json` 单标量 + 设备级配对 Cookie 门禁**（与 `docs/运维收口计划.md` 第 2 节一致，复核后确认可行且最小。**不引入** localStorage 标记、独立 client token、设备列表/UI/DB）。

### 规则
1. **登记**：iPad 打开 `http://<host>:8080/siri/pair`，输入 `SIRI_HTTP_TOKEN`（POST JSON body，不进 URL）。服务端生成 `deviceId=randomUUID()` → 写入 `run/controller.json`（`{"deviceId":"..."}`，gitignore，重启保持）→ 下发 `Set-Cookie: siri_pair=<deviceId>:<HMAC(SIRI_HTTP_TOKEN,deviceId)>; HttpOnly; SameSite=Strict; Path=/; Max-Age=1年`。
2. **正常连接**：WS 握手读 Cookie → HMAC 校验 `conn.paired` + `conn.controller = deviceId === controller.json.deviceId`。只有 `conn.controller` 才可能：收到 `play.req`（`sendPlayRequest` 候选集只含 controller）、触发 offline `dispatch`、其 `play.ack` 被 pending/offline 结算。
3. **其他设备访问 WebUI**：正常加载、正常登录酷狗、正常认证 WS（token 本就内嵌公开脚本，无法避免），但**永不收 play.req、不能抢命令、其 ack 被忽略**——满足“不抢走目标 iPad”边界。
4. **重新配对新设备/换 iPad**：再次 `/siri/pair` → 覆盖 `controller.json` → 旧 iPad 的 Cookie 仍在但 deviceId 不匹配，**立即失去资格**。
5. **清 Safari 网站数据/换设备**：Cookie 随 web data 清除（非 localStorage，但属于同一“网站数据”）；重新 `/siri/pair` 输一次 token 即可（限 5 次/分）。
6. **SW 更新不影响登记**：Cookie 与 `controller.json` 均在 SW/构建体系之外。
7. **token 泄露面**：配对 Cookie 是 HMAC 派生、HttpOnly、SameSite=Strict，JS 不可读；`/siri/pair` 用 POST body 不入 access log；`?token=` 删除后 `SIRI_HTTP_TOKEN` 只出现在 Header 与快捷指令。残余风险：同 Wi-Fi 攻击者若抓包窃取 Cookie 可顶替控制器——家庭局域网可接受，运维文档注明“不对公网暴露”。
8. **`sessionState.paired` 修复**：改为读取服务端回传（如 `/debug/status.controller`）或移除该字段，不再用 `document.cookie`。

### 非目标设备影响（代码确认）
- 连接数可以很多（`clients` Set 无驱逐），认证+心跳照常，无害。
- 离线 queued 命令只由 controller 认证时触发 dispatch；在线路径只发 controller。
- 不引入任何“关闭旧连接”逻辑——非 controller 连接共存即可，无需抢占保护。

## 6. Siri 快捷指令最终流程

### 现状审计（对照任务 §五）
- 在线成功返回 `200 {ok:true,song}`，**没有 `status` 字段**；离线返回 `202 {ok:true,status:"queued",reqId}`；失败返回 `200 {ok:false,error}`；401/504 返回 JSON body。→ 快捷指令只看 `status` 会**漏掉在线失败**（`status` 为空 → 静默结束）。
- `status != queued` 时直接结束：在线成功合理（安静），**在线失败不合理**（必须提示）。
- “查找标签页”用 URL 完全相等：过严（`/#/library`、`/`、参数都会失配）→ **删除**。
- “打开 URL”实测会**新开标签页/整页加载**（日志证据：queued→GET /→新页）→ 新页无手势，Safari 禁自动播放 → “播放失败”弹窗。这是**已接受的产品限制**（新页面需人工播放一次解锁，或站点设置“允许自动播放”）。
- queued 后切换标签页是否唤醒原页面：仅当该 tab 存活且置前时原地唤醒（README 实机确认）；不存在/被回收时只能新开页。
- 状态查询接口：**只对离线 queued 命令有意义**（`GET /api/siri/commands/:reqId` 查的是 offlineCommand 快照，在线路径 HTTP 响应本身就是结果）。保留。
- 轮询：**最多 2 次**（6s + 再 3s）。第 1 次在 6s 时查（页面加载+唤醒+重连+搜索，日志实测约 3–6s）；未成功再等 3s 查一次；仍失败才提示。

### 推荐动作步骤（Shortcuts App 中）
```
1. 听写文本 → 歌曲名
2. 获取URL内容（POST http://192.168.1.100:8200/api/siri/play）
     头部: x-siri-token: <SIRI_HTTP_TOKEN>；Content-Type: application/json
     请求体: {"query":"<歌曲名>"}
     返回体转为字典 → 取 status / ok / error / reqId
3. 如果 status == "queued"：
      a. 打开URL http://192.168.1.100:8080/     （把 WebUI 置前台/唤醒）
      b. 等待 6 秒
      c. 获取URL内容（GET http://192.168.1.100:8200/api/siri/commands/<reqId>，带 x-siri-token）
         → status == "succeeded" → 结束（安静）
         → 否则 → 等待 3 秒 → 再查一次 → "succeeded" → 结束
         → 仍未成功 → 显示通知（含当前 status/error）
4. 否则如果 ok == false：
      显示通知（error 原样或映射为中文，见下）
5. 否则（ok == true 且有 song）→ 结束（在线成功，安静，无需通知）
```
- **必须提示**：`ok==false`（含 401 UNAUTHORIZED、504 TIMEOUT、SEARCH_FAILED/NO_RESULTS/SESSION_EXPIRED/SESSION_REAUTH_REQUIRED/AUTOPLAY_BLOCKED/PLAY_FAILED 等）。可做**一层** if 把 `SESSION_EXPIRED`/`SESSION_REAUTH_REQUIRED` 映射为“请打开 WebUI 重新登录”，其余显示原码即可，**不要**做多层 if。
- **安静结束**：在线成功；queued→succeeded。
- **删除**：`查找标签页`（精确匹配）步骤、`status != queued` 时的静默结束、“播放/暂停”动作（已实机确认无效）。
- **缺失**：失败分支的通知；在线失败会被当前版本吞掉的兜底。
- **避免无意义打开 WebUI**：只有 `status=="queued"` 才打开 URL，在线成功/失败都不打开。

## 7. 播放成功判断（消除假成功）

**结论：现 ACK 为假成功**（代码确认，见第 3 节）。修复方案（不改 MoeKoeMusic 源码，改注入客户端）：

1. `addSongToQueue` 返回 `result.song` 后，**轮询 `player.playing === true`**（每 100ms，最长 ~1500ms）。`playing` 由音频元素 `play` 事件驱动（AudioController.js:237-247），只有 `audio.play()` 真正成功才会置 true；autoplay 被拦则始终 false。
2. 收敛为 true → `play.ack ok:true`。
3. 始终 false → 用 `navigator.userActivation?.hasBeenActive`（不存在时视为 true）区分：`false` → `AUTOPLAY_BLOCKED`，`true` → `PLAY_FAILED`。
4. `shouldPlayNext` 改映射 `PLAY_FAILED`（本就表示取 URL 失败/无版权，非自动播放拦截）。
5. 无无限重试、无模拟点击、不建第二个 Audio。`player.playing` 经 `defineExpose` 暴露（PlayerControl.vue:1826）+ public proxy 自动解包，返回布尔，客户端可读（README 已确认 `playingType:'boolean'`）。

**真实条件定义**：ACK 成功 = “addSongToQueue 取到 URL 且 `audio.play()` 已开始（play 事件触发、playing==true）”。命令已发送 / addSongToQueue 已返回 / 真正出声 三者由此精确区分。

## 8. 账号与多端登录审计

代码确认（源自 MoeKoeMusic 源码审计）：
- **状态保存**：登录成功写 `localStorage['MoeData']`（Pinia persisted，含 `UserInfo/Config/Device`）；API 同时回写 Cookie（token/userid/t1/vip_type/vip_token/dfid + KUGOU_API_*，server.js:396-417）。认证主要靠 **Authorization Header（MoeData 拼装）**，Cookie 为辅助（withCredentials:true，request.js:14）。
- **Control Server 不依赖浏览器会话**：搜索在 iPad 浏览器内以同源身份执行；会话恢复走 `login_by_token`→WS reauth→Windows 侧账号密码，不读 iPad Cookie。
- **密码明文**：仅在 `.env`（配置级，已确认不落日志/不进 status/不回传客户端）；`session-auth.js` 用 POST JSON body，不把凭据放 URL。
- **登录失效检测**：WebUI 自身**从不调 `/login/token`**（grep 确认 src/ 零引用）→ 由 siri-control 客户端每 45min 前台刷新 + 搜索遇 152/status2 触发恢复。
- **多端登录影响**：MoeKoeMusic API 无状态、无服务端会话表；**代码层面没有任何踢人/互斥逻辑**，`/login/device/kick` 模块还是坏的（未引用且引用未定义变量）。其他设备登录是否使 iPad token 失效**取决于酷狗上游**（推测，无法在本仓库验证）——系统对此的兜底是 Phase 5.6 恢复链路，这是正确且最小。
- **最小恢复流程（可接受）**：登录失效 → Siri 报 `SESSION_EXPIRED`/`SESSION_REAUTH_REQUIRED` → 用户打开 WebUI 手动验证一次（或自动恢复成功则无感）。**前提**：修复 P1 熔断（避免错误密码/风控下无限重试），并保持配对 Cookie 存在。

## 11. 精简后的功能边界

**必须保留**：WS 认证/心跳/自动重连、单条 pending、command id+ACK、离线单槽+状态接口、唯一控制器（新增）、配对/恢复、45min 会话刷新、健康检查（扩展）、构建校验、错误码、日志无泄密、PowerShell 启停。

**明确不做**：多播放设备/设备选择 UI/多房间/多用户/DB/OAuth/JWT/RBAC/播放历史/管理后台/云端/公网访问/TLS 自动化/pause-next-volume 扩展接口/服务端搜索/解析播放 URL/`new Audio()`/模拟点击/静音保活/长队列。

## 13. 最终判断

1. **是否已“功能够用”**：核心链路（在线点歌、离线 queued、前台唤醒自动投递、登录续期/恢复）已实测可用，**单 iPad 单浏览器场景下功能基本够用**。但作为“家庭局域网长期运行”的目标，**尚未达到收口标准**——三个 P0 缺口（唯一控制器绑定、ACK 真实性、6521/防火墙收口）是真实存在的，且其中两个正是“多设备访问时抢走目标 iPad”与“succeeded 但没声音”这两条最直接影响使用体验的边界。

2. **是否适合停止新增功能、进入维护阶段**：**暂不**。应先用 Phase 2/3 两个小改动消除 P0 缺陷（都是单文件级别的客户端/服务端改动，不改 MoeKoeMusic 源码），完成 Phase 5 网络收口后再冻结功能进入维护。届时“唯一 iPad + 家庭局域网”的边界才真正成立。

3. **上线前还必须完成**：Phase 2（唯一控制器）、Phase 3（真实 ACK）、Phase 5 的 6521 回环 + 防火墙收敛；以及 P1 的 reauth 熔断与 `git init`（防密码填错时无限撞风控、防代码零备份）。

4. **可以永远不做**：多播放设备/设备选择 UI/多房间/多用户/数据库/OAuth/JWT/RBAC/播放历史/管理后台/云服务/公网访问/TLS 自动化/暂停-上一首-下一首-音量等扩展接口/服务端搜索与解析播放 URL/`new Audio()`/模拟点击/静音保活/长队列 pending/消息中间件/Redis/Docker/nginx 多层代理。这些均与“单 iPad 家庭点歌系统”的目标无关。
