# 《单 iPad 运维收口计划》

> 基于源码、测试、运行日志、端口与防火墙状态的审计结论（2026-08-17 实机验证）。
> 每一项均对照真实代码，不是文档复述。

## 1. 当前架构与真实运行状态

```
Siri 快捷指令 → POST :8200/api/siri/play（x-siri-token）
  ├─ 有 WS 客户端 → pending → sendPlayRequest 选 1 个目标 → play.req → 客户端
  │                   搜索(/api/search/complex 同源+Authorization) → extractFirstSong
  │                   → PlayerControl.addSongToQueue → play.ack → HTTP 200
  └─ 无客户端 → offline-command 单槽 → 202 queued → 下个认证连接自动 dispatch
```

运行态实测（全部验证）：

- 端口：`0.0.0.0:8080`、`0.0.0.0:8200`（server/index.js, PID 8756）；**`0.0.0.0:6521` + `[::]:6521`（api/app.js, PID 15652）——6521 暴露全接口，违反约束**。
- 防火墙：两条 **"Node.js JavaScript Runtime" Allow（Private + Public，TCP/UDP Any，程序 node.exe）**——node 全部端口、含公用网络入站全开。
- 测试：`npm test` 172/172 通过；`npm run verify:web` 12/12 通过（`siri-control.fe6b848352.js` hash 匹配、sw.js 含 index.html revision、MoeKoeMusic 工作树 clean）。
- `/health` → `{"ok":true,"protocol":1}`，但**不含上游/控制器状态**。
- **MoeKoeSiriControl 不是 git 仓库**——服务端代码无版本管理与备份。
- 开机自启：启动文件夹 `MoeKoeSiriControl.vbs` 存在，登录后隐藏窗口跑 start-all.ps1。
- 日志：`run/web-host.log` 42KB、`api.log` 16KB，无轮转；扫描无 token/密码/Authorization/Cookie 泄漏（`req.path` 不含 query，安全）；api.log 仅记录路由与 hash。
- MoeKoeMusic 提交 `55e9a70`（MediaSession）与 `d0c1c37`（音频输出）均在，工作树 clean。

## 2. 唯一播放设备的精确定义（最终方案）

**唯一 controller = 持有与 `run/controller.json` 记录的 deviceId 一致的配对 Cookie、且通过 WS 认证的连接。** 只有它 command-eligible。

- 配对 Cookie 改为设备级：`siri_pair = <deviceId>:<HMAC(SIRI_HTTP_TOKEN, deviceId)>`（deviceId 由服务端每次配对生成，HMAC 防伪造）。
- `/siri/pair` 成功时把新 deviceId 写入 `run/controller.json`（一行 JSON，gitignore，重启保持）。
- WS 握手解析 Cookie → `conn.paired`（HMAC 校验）+ `conn.controller`（deviceId === controller.json）。
- `sendPlayRequest` 与 offline `dispatch` **只考虑 `conn.controller` 为真的连接**；其余连接照常认证/心跳/reauth，但永不收 play.req。
- **重新配对新设备 → 覆盖 controller.json → 旧 iPad 的 Cookie 仍在但立即失去资格**。
- **Cookie 被清 / Safari 数据清空 / 换 iPad** → 重新打开 `/siri/pair` 输一次 SIRI_HTTP_TOKEN 即可（按 IP 限 5 次/分钟）。
- 无设备列表、无 DB、无 UI，`controller.json` 是唯一标量。

## 3. 多端登录/多 WebUI 时的行为边界

- **多个 WebUI 打开**：全部能认证 WS（脚本内嵌 WS token），但只有 controller 能收 play.req。手机/电脑页面正常使用 WebUI、正常登录酷狗，**不会抢命令、不会收到 play.req、不会 ACK**。
- **官方 App / 其他 WebUI 登录挤掉 iPad 会话**：iPad 搜索遇 152 → `login_by_token` 刷新 → 失败 → 经 WS 请求 `session.reauth.req`（仅配对连接可用）→ Windows 侧账号密码登录恢复，最多按第 9 节熔断策略。**不无限重登、不反挤官方 App 会话**。
- 结论：账号在 N 端登录是常态，系统只负责"指定 iPad 会话失效时的有限恢复"，不维持任何其他端。

## 7. 每个缺失项的实施方案

### A. 唯一控制器绑定（P0）
- **触发场景**：手机/另一电脑打开 WebUI → 抢到 play.req；未配对浏览器可当播放端。
- **当前行为**：`sendPlayRequest` 选"非 loopback 最近认证"；offline `onAuthenticated` 对任意认证连接派发。
- **期望行为**：只有 `conn.controller` 连接收 play.req；重启后资格仍在；重配对替换旧资格。
- **修改文件**：`server/pairing.js`（设备级 Cookie 派生/校验）、`server/web-host.js`（配对写 controller.json + 下发新 Cookie）、`server/control-server.js`（握手解析 deviceId、`sendPlayRequest` 加 controller 门禁）、`server/index.js`（onAuthenticated 透传 conn.controller）、`test/pairing.test.js`、`test/control-server.test.js`、`test/http-api.test.js`、`test/offline-command.test.js`、README。
- **最小实现**：
  1. `pairing.js`：`derivePairValue(secret, deviceId)`、`parsePairCookie(header, secret)` → `{deviceId, ok}`；保留旧单参派生仅在兼容期。
  2. `web-host.js` POST /siri/pair：`deviceId = randomUUID()`；写 `run/controller.json`（`{deviceId}`）；`Set-Cookie: siri_pair=<deviceId>:<hmac>; HttpOnly; SameSite=Strict; Path=/; Max-Age=1年`。
  3. `control-server.js` 握手：`conn.paired = ok`；`conn.controller = ok && deviceId === controllerState.deviceId`（从 index.js 注入 `isController(deviceId)`，读取 controller.json 缓存）。
  4. `sendPlayRequest`：候选集合改为 `conn.controller`；offline `dispatch` 同样只由 `onAuthenticated` 中 `conn.controller` 触发。
- **测试方法**：新增——配对一个"controller"WS（正确 Cookie），另开一个"非 controller"（合法配对 Cookie 但 deviceId 不同 / 无 Cookie），断言 play.req 只发给 controller；换设备重配对后旧连接不再被选；重启（重新 createControlServer + 重新读 controller.json）后资格保留；伪造 Cookie 拒绝。
- **通过标准**：`npm test` 全绿；HTTP 全链路在多客户端（1 controller + 2 非 controller）下只命中 controller；旧配对 Cookie 升级需重配一次（文档说明）。
- **回滚**：恢复旧 `derivePairValue` 单参逻辑，删除 controller 门禁；iPad 无需重新配对（旧 Cookie 兼容）。若已 git 化，直接 revert 该提交。

### B. ACK 真实性（P0）
- **触发场景**：新标签页被快捷指令打开（无用户手势）→ Safari 禁自动播放 → "播放失败"弹窗，但 ack ok:true、status=succeeded。
- **当前行为**：`commandHandler.execute` 在 `addSongToQueue` 返回 `{song}` 即发 `ok:true`（siri-control.cjs:885-888）。
- **期望行为**：ACK true 仅当"播放已收敛到 playing 状态"；否则区分 AUTOPLAY_BLOCKED 与 PLAY_FAILED。
- **修改文件**：`client/siri-control.cjs`（`createCommandHandler.execute`），测试 `test/command-handler.test.js`、`test/client-core.test.cjs`。
- **最小实现**（不改 MoeKoeMusic，免重建）：
  1. `addSongToQueue` 返回 `{song}` 后：轮询 `player.playing === true`，最长约 1500ms（每 100ms）。
  2. 变 true → `ok:true`；始终 false → 用 `navigator.userActivation?.hasBeenActive`（不存在时视为 true）判定：`false` → `AUTOPLAY_BLOCKED`，`true` → `PLAY_FAILED`。
  3. 交叉校验 `player.currentSong?.hash`：若已切到别的歌（shouldPlayNext 已提前处理，此分支兜底）→ `PLAY_FAILED`。
  4. `shouldPlayNext` 从映射到 `AUTOPLAY_BLOCKED`（siri-control.cjs:889-892）改为 `PLAY_FAILED`——那本意是"取 URL 失败/无版权"，不是自动播放拦截。
  5. 无无限重试、无模拟点击、不建第二个 Audio。
- **测试方法**：fake player 注入（playing 初始 false 后变 true / 一直 false + userActivation 开关）断言 ack 码；应验证 ack 延迟 ≤ 收敛窗口、错误码映射正确。
- **通过标准**：`npm test` 全绿；真机复现"新标签页"场景返回 `ok:false AUTOPLAY_BLOCKED` 且**不再显示 succeeded**。
- **回滚**：恢复 execute 原逻辑；纯客户端脚本，重新 `npm run build:web` + `verify:web`。

### C. 登录恢复熔断（P1）
- **触发场景**：.env 密码填错 → 每 60s 自动重登一次、永不停；风控命中 → 每 60s 再撞。
- **当前行为**：session-auth.js `fail()` 一律 60s 冷却；无小时预算、无硬停。
- **期望行为**：`AUTH_REJECTED` / `RISK_REQUIRED` → **硬停自动尝试**（等人工干预，如改 .env 后重启，或手动 `recoverSession()` 前 reset）；瞬时错误（UPSTREAM/TIMEOUT）→ 60s 冷却但**每小时上限 5 次**。
- **修改文件**：`server/session-auth.js`（`hardStop` 状态 + 小时计数 + `reset()` 语义扩展）、`server/http-api.js` `/debug/status` 暴露 `sessionAuth`（configured/hardStopped/cooldownUntil/lastCode，无凭据）、`test/session-auth.test.js`、`test/control-server.test.js`。
- **最小实现**：`login()` 前检查 `hardStop`（返回原码）；新计数窗口 `maxAttemptsPerHour=5`，耗尽返回 `UPSTREAM_UNAVAILABLE`（detail:'throttled'）；`reset()` 清 hardStop（供 `recoverSession()` 手动触发一次）。
- **通过标准**：错误密码后 1 次登录、之后 30 分钟内不再有上游调用；风控后不再自动撞；小时内第 6 次被节流；`npm test` 全绿。
- **回滚**：移除 hardStop/小时预算逻辑。

## 8. 应删除/停用的功能及理由

- **`?token=` 鉴权**：进 URL/历史/代理日志，无收益（Header 已够）→ 删。
- **`sendPlayRequest` 的 broadcast 回退分支**（http-api.js:65）：死代码 → 删，仅保留 `sendPlayRequest`。
- **success grace（PENDING_SUCCESS_GRACE_MS）**：单控制器下无竞态 ACK → 删，pending 首个 ACK 即结算（同步删/改 pending.test.js 的 grace 用例，其余保留）。
- **`shouldPlayNext → AUTOPLAY_BLOCKED` 映射**：语义错误 → 改为 PLAY_FAILED。
- **多端抢答相关 README 段落**：随方案替换为"唯一控制器"语义。
- **删除项均不是"调试功能"**：`probe/probeAll/recoverSession/__siri.play/debug/status` 全部保留为维护入口（文档标注用途）。

## 9. 登录被挤掉时的有限恢复策略（定案）

1. `login_by_token` 每 45 分钟前台刷新（现有）→ 成功即无事。
2. 搜索遇 152 → 刷新一次 → 仍 152 → `session.reauth.req`（仅配对连接）→ Windows 账号密码登录。
3. **熔断**：`AUTH_REJECTED`/`RISK_REQUIRED` 命中后硬停自动尝试（不重登、不撞风控），Siri 返回 `SESSION_REAUTH_REQUIRED`、iPad 自动进 `/#/login` 人工处理一次；瞬时错误（超时/网络）60s 冷却 + **每小时 ≤5 次**，超出返回节流码。
4. 客户端每命令至多恢复一次（现有 `createRecoverySearch` 单飞/单次重试，保持不变）。
5. 与官方 App 互不干扰：恢复是一次性低频登录，不维持双会话，不循环。
6. 人工状态可见：`window.__siri.sessionState` + `/debug/status.sessionAuth`（新加）。
